# Equivalence-checker audit — rule mining (2026-07-10)

Three audit lenses (code review, adversarial probes against the compiled 0.4.2 core,
re-verification of 840 stratified dev_7-3 rules with 100k-point wide-domain sampling +
sympy). VERDICT: the checker is NOT sound or reproducible as shipped; the planned 7-4
mine must not run before the hardening below. All findings verified by execution.

### [CRITICAL] The equivalence check has no guard against all-NaN (or all-inf) vacuous agreement: allclose with equal_nan=True accepts any (source, candidate) pair that is NaN on every sampled row, certifying provably FALSE rules; the shipped dev_7-3 ruleset already contains this class and the deployed engine misfires on them.

Evidence: rust/eval.rs:222-245 (allclose: both-NaN rows 'continue', same-sign inf rows 'continue', no requirement that ANY row be informative) and rust/worker.rs:64-91 (equivalent_no_const applies it unconditionally); the Python reference is identical (src/simplipy/engine.py:2531 np.allclose(..., equal_nan=True)). EXECUTED: _core.equivalent_no_const(['log','neg','pow2','x0'], ['asin','cosh','x0'], X~N(0,5) 1024 rows) returns True with both sides 100% NaN on the sample, yet at x0=0 source=-inf and candidate=pi/2 (asin(cosh(0))=asin(1)); _core.find_rule then selects ['asin','cosh','x0'] as the rule target. n_rows=0 also vacuously returns True (empty allclose policy). SHIPPED EVIDENCE: scanning dev_7-3 rules.json, 5,125 of 30,200 wildcard rules have BOTH sides >99% NaN on an N(0,5) sample, including provably false rules ('asin','cosh','_0')->nan (false at _0=0: pi/2), ('acosh','cos','_0')->nan (false at 0: acosh(1)=0), ('atanh','cosh','_0')->nan (false at 0: +inf), ('pow','(-1)','_0')->nan (false at every even-integer _0: value 1). END-TO-END: engine.simplify(['asin','cosh','sin','x0']) -> ['float("nan")'] although the true value at x0=0 is pi/2; simplify(['pow','(-1)','pow2','x0']) -> nan although (-1)**4=1 at x0=2. The test suite cannot catch this: tests/test_equivalence.py:65-73 explicitly masks out rows where the original is NaN. Cascade (audit item 6): a false short rule enters the rule set via set_rules for every later length, and mine_one_length Kruskal-prunes any longer source it shortens (rust/engine.rs:248-250), silently masking correct rules at lengths 5-7 while deduplicate_rules (utils.py:521, keeps shortest target per canonical source) preserves the false rule.

Suggested fix: Add an informativeness gate to both decision paths before the new mine: require a minimum count/fraction of rows where BOTH sides are finite (e.g. >=100 of 1024) in equivalent_no_const/candidate_matches, and raise the fit path's bail from 'n_const > n_valid' to the same minimum (fit.rs:198,577); reject (or route to a quarantine list) any pair below it. Optionally special-case genuinely-all-NaN identities by proving NaN-ness symbolically, not by sampling. Re-mine; also audit/purge the existing dev_7-3 NaN-rule family if it stays in service.

### [MAJOR] The mine is non-reproducible as shipped: the default X is unseeded, and both the source list and the candidate library are built by iterating Python sets whose order depends on PYTHONHASHSEED, which changes per-source seeds and select_best discovery-order tiebreaks — different runs yield different rulesets even on identical hardware.

Evidence: src/simplipy/engine.py:2768 'X_data = np.random.normal(loc=0, scale=5, size=(1024, len(dummy_variables)))' (no seed); engine.py:2633-2638 (candidates) and engine.py:2652 (sources) iterate set objects; EXECUTED: the same 5-element set of expression tuples printed in different orders under PYTHONHASHSEED=1 vs 2. The per-source challenge RNG is seed=length + source index (rust/engine.rs:252 'seed.wrapping_add(idx)', seed=length from engine.py:2653-2655), so a permuted source order re-assigns challenge streams; candidate order sets library discovery order, which is the tie-break in select_best (rust/worker.rs:146 stable sort by <constant> count only). The Rust side itself is deterministic given fixed inputs (splitmix64 Rng fit.rs:261-282; rayon par_iter().filter_map().collect() is order-preserving), so the nondeterminism is entirely Python-side. Note seeds also overlap across lengths (length L, idx i and length L+1, idx i-1 share a seed) — harmless but ugly.

Suggested fix: For the solomon run: (1) generate X once with a recorded seed (or np.random.default_rng(seed)) and persist it alongside the ruleset; (2) sort sources and candidates deterministically (e.g. lexicographically) in _find_rules_native before building the library and before each mine_one_length call; (3) set PYTHONHASHSEED explicitly as a belt-and-braces measure; (4) derive per-source seeds from a hash of the source tokens rather than the list index.

### [MAJOR] Mined-under vs applied-under semantics divergence on signed zero: the Rust miner's inv and div kernels return +inf for a -0.0 argument/divisor, while the deployed numpy array-branch realizations (what flash-ansr actually evaluates with, and what the Python reference miner uses) return -inf — so the native miner can certify rules that are false under deployment semantics, and Rust and Python reference miners disagree; exact zeros are routine in mining because sign-combo 0 zeroes source constants.

Evidence: rust/numeric.rs:139 'inv => |x| if x == 0.0 { f64::INFINITY ... }' (matches -0.0 too) and numeric.rs:205-217 op_div (y==0 -> sign of x, ignoring divisor sign) vs src/simplipy/operators.py:26-37 inv array branch 'return 1 / x' and operators.py:40-45 div array branch 'return x / y' (raw numpy). EXECUTED: _core.evaluate_batch(['inv','x0'], x=[-0.0, 0.0]) = [inf, inf] while simplipy.operators.inv(np.array([-0.0, 0.0])) = [-inf, inf]; _core div(1, -0.0) = inf vs operators.div arrays = -inf. Zero arguments arise realistically from the {-1,0,+1} sign combos (rust/worker.rs:42-56, engine.py:2529): e.g. C=0 makes 0*x produce ±0.0 with row-dependent sign, splitting the Rust (+inf everywhere) and numpy (row-dependent ±inf) verdicts. operators.py is additionally internally inconsistent scalar-vs-array (scalar inv(0)=+inf, array 1/-0.0=-inf). Otherwise op parity is sound: all 33 unary + 5 binary miner-reachable ops resolve to raw f64/system-libm kernels shared by folding, mining and the improved simplify line (numeric.rs:135-191 unary_fn/binary_fn is the single source of truth); no hidden clamping/protection was found; pow uses C pow (0**0=1, neg**frac=NaN, matching np.power), pow1_3/pow1_5 real odd roots match the numpy where-branch.

Suggested fix: Decide one semantics and align all three surfaces: either make the Rust inv/div kernels IEEE-signed-zero-aware (x==0.0 branch checks signum, matching the numpy array branch that deployment actually executes), or fix operators.py's array branches to match the documented scalar semantics. Given rules must hold under deployed evaluation, matching numpy's array semantics in numeric.rs is the safer direction; re-run the M1 parity differential afterwards.

### [MINOR] The value governing the native mine is find_rules' constants_fit_challenges=5 / constants_fit_retries=5, not the FFI defaults of 16: engine.py passes them positionally into mine_one_length, so a mine launched via find_rules with defaults gets 3x less challenge coverage than the FFI-default surface suggests.

Evidence: src/simplipy/engine.py:2653-2655 'self._core.mine_one_length(sources, library, max_target_pattern_length, constants_fit_challenges, constants_fit_retries, length)' vs rust/lib.rs:517 '#[pyo3(signature = (sources, library, max_target, challenges=16, retries=16, seed=0, ...))]' and find_rules defaults engine.py:2682-2683 (=5). Suggested fix: Pick the intended verification strength explicitly for the new mine (challenges=16 is cheap insurance for constant-bearing sources) and pass it deliberately; surface rtol/atol as find_rules parameters so the run's tolerance is recorded.

### [MINOR] Sampling-power limits are real but unguarded and undocumented: atol=1e-8 makes every row where both sides are <1e-8 in magnitude uninformative (69% of rows for exp(-x0^4) under N(0,5)); the 1024-row N(0,5) X never samples beyond |x|~19.5 so all tail behavior (overflow regions, exp/cosh saturation) is unverified; and the SAME single X is reused for every decision in the whole mine with no independent confirmation sample.

Evidence: EXECUTED: fraction of rows with exp(-x0^4) < 1e-8 is 0.692 on the default sample; max|X| over 1024x4 N(0,5) draws = 19.5. rtol asymmetry (|a-b| <= atol + rtol*|b| with b=candidate, rust/eval.rs:239) matches numpy's argument order in the Python reference (engine.py:2531), so it is parity-correct but means tolerance scales with candidate magnitude. The fit path's false-accept risk (fit succeeding on the sample but not as an identity) is bounded by the same coverage: the gate allclose(y_target, fitted) runs over ALL rows including the NaN-pattern (EXECUTED: fitting '<constant>' to a target with 1 finite row correctly returns False because the 1023 NaN rows fail against the finite fitted constant), so false accepts require the low-coverage channel of the critical finding.

Suggested fix: Alongside the informativeness gate: add a second, independently-drawn confirmation X (accept only if both samples pass) — this is cheap (one extra eval per accepted pair) and converts one-sample coincidences into ~squared-probability events; consider a small deterministic set of structured probe points (0, ±1, integers, ±large) appended to X to cover exceptional points like asin(1)/acosh(1) and integer exponents.

### [MINOR] Performance: candidate_matches re-evaluates the SOURCE tape per candidate per challenge even when the source is constant-free (identical y every time), costing ~challenges x |library| redundant 1024-row evaluations per source — the bulk of the measured 4.75-6.5 s per unmatched length-7 source; hoisting makes exhaustive length-5 mining much more tractable.

Evidence: rust/worker.rs:206-215: the challenges loop samples rc (empty for n_src_const=0) and re-runs src_tape.eval_columns for every (challenge, combo, candidate) triple; for a const-free source combos=[[]] and the y is bit-identical across all challenges AND all candidates, yet it is recomputed ~5 x 18,115 = ~90k times per source. The candidate side is already hoisted (y_const_free precomputed at library build, worker.rs:272-276); the source side is not. Measured: find_rule_lib on unmatched length-7 sources = 4.75-6.5 s each (challenges=5, retries=5, 18,115-candidate library, single-threaded).

Suggested fix: In find_rule_with_lib, precompute the source y once per (challenge, combo) OUTSIDE the candidate loop (restructure: for each challenge/combo, evaluate source once, then test all surviving candidates), and skip the challenges loop entirely when n_src_const==0. Expected ~5-50x per-source speedup for const-free sources, which dominate the universe.

### [CRITICAL] Vacuous-NaN false accepts: equal_nan=True allclose plus N(0,5)-only sampling certifies 'f -> nan' (and f -> g) rules for functions that are NaN on the sample but finite on reachable inputs; this class is already realized as wrong rewrites in the SHIPPED dev_7-3 ruleset.

Full native find_rule confirms: find_rule(asin cosh x0)=['float("nan")'], find_rule(acosh div5 div5 x0)=['float("nan")']. Shipped asset: 7879 rules with rhs float("nan") (4989 with wildcard lhs) including ('asin','cosh','_0'), ('acos','cosh','_0'), ('acosh','cos','_0'), ('pow','(-1)','_0'), ('pow','tan','np.e','_0'). ### [CRITICAL] Saturation/near-constant false accepts within the rtol=1e-5/atol=1e-8 gate: <=7-token in-vocab sources that are near-1 (tanh towers) or near-0 (exp towers) are deterministically certified equal to the 1-token constants '1'/'0', and small-argument linearizations sin(a*x)->a*x with unbounded application error are accepted; all shapes are in scope for the planned 7->4 mine.

### [MAJOR] Sharp tolerance floor at rel 1e-5 relative to the CANDIDATE: any two genuinely different expressions agreeing within 1e-5 relative everywhere on-sample are certified equivalent, with a hard cliff (no margin/hysteresis), and rule chaining compounds these per-rewrite errors.

Evidence: Probe (d): source (2+delta)*x0 vs candidate mult2(x0): accepted 20/20 at delta_rel=9.95e-6, rejected 20/20 at delta_rel=1.01e-5 -- the boundary sits exactly at rtol=1e-5 (rust/eval.rs:239, |a-b| <= atol + rtol*|b|, b = candidate, asymmetric). Finding-2's tanh/exp tower family are concrete in-vocab pairs that land inside the band, so 'two genuinely-different mined expressions within it' is realized, not hypothetical. Each false rule application injects up to ~1e-5 relative error, and simplify applies rules iteratively (max_iter loop), so chained rewrites can accumulate multiples of it.

Suggested fix: Keep 1e-5 as the screening tolerance but add a confirmation pass at a much tighter tolerance (e.g. rtol=1e-9) on the winning candidate before a rule is recorded; genuine identities pass both (ULP-level agreement), tolerance-band impostors fail the second.

### [MAJOR] Mining runs are irreproducible and marginal rules enter stochastically: the evaluation X is sampled UNSEEDED per find_rules call, and the Rust challenge seed is just the source length, so near-threshold rules (saturation/linearization/NaN-coverage families) flip in and out between otherwise identical mines.

Evidence: engine.py:2768 'X_data = np.random.normal(loc=0, scale=5, size=(1024, len(dummy_variables)))' with no seed parameter anywhere in find_rules' signature (engine.py:2675-2689); engine.py:2653-2655 passes 'length' as the mine_one_length seed (deterministic but X still random); the pure-Python worker path uses global np.random unseeded (engine.py:2527). Empirically, sin(x/2500) ~ x/2500 accepted on 96/100 independent X draws: about 1 mine in 25 would exclude a rule the other 24 include, and acceptance of the whole marginal family depends on the max|x| order statistic of one unseeded draw. Also note the challenge count actually used is constants_fit_challenges=5 (find_rules default, engine.py:2682), not the FFI default 16 (rust/lib.rs:384) -- and for const-free candidate pairs challenges provide NO protection at all (y is identical each round, worker.rs:77-90: y_cand computed once, source has 0 params so every challenge re-evaluates the same deterministic pair), so the single X draw is the only defense.

Suggested fix: Add a seed parameter to find_rules and thread it to X generation and the FFI seed; for the big 7-4 mine, additionally union two or three independent X draws (or one N(0,5) + one wide log-uniform draw) so acceptance is not a single-sample order-statistic event, and record X (or its seed) in the ruleset provenance.

### [MINOR] Measure-zero and f64-overflow-region domain changes are accepted by design and shipped: x0/x0 -> 1 (NaN at 0 rewritten to 1) and log(exp(x0)) -> x0 (differs for |x0|>709 where exp overflows to inf), while the NaN-mismatch guard correctly rejects the harmful direction (sqrt(x0)^2 -> x0, exp(log(x0)) -> x0, sqrt(x0^2) -> x0 all rejected 50/50, sqrt(x0^2) -> abs(x0) accepted).

Evidence: Probe (b) over 50 X-seeds: ('/','x0','x0') ~ '1' accepted 1.00 (div(0,0)=NaN per numeric.rs op_div, but x=0 has probability 0 under the continuous sample); ('log','exp','x0') ~ 'x0' accepted 1.00 (equal on all |x|<709; at application a bound subtree value v with |v|>709 gives log(inf)=inf vs v). Suggested fix: Document the policy explicitly in the mining spec: domain-enlarging rewrites (NaN/inf -> finite on measure-zero or overflow-region sets) are accepted; domain-shrinking ones are rejected by the NaN-mismatch gate. If exact f64 semantics ever matter downstream, add the wide-range challenge X from finding 1, which would demote log(exp(_0))->_0 as well.
